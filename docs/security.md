# Security

Flockcast has accounts and projects. Each person signs up with an email and password and sees only their own projects, rehearsals and API keys. Other apps reach one project through an API key. Everything lives in one SQLite file. This page lists each common web-app risk, what Flockcast does about it, and where the code is. Items that do not apply say why.

It shares its security baseline with Creator OS, but runs on its own and depends on no other app.

| Risk | Status | How |
|---|---|---|
| Cross-site scripting (XSS) | Protected | React escapes all text, model replies and reports included. Reports are markdown rendered to React elements by a small parser (`web/src/components/shared/markdown.tsx`), never to HTML. The only raw markup is the mascot stickers, built from static art in `pip-art.ts` with no user or server input. A Content-Security-Policy allows scripts from the app's own origin only, with no inline scripts, and fonts from the app's origin only (`src/http/middleware/security-headers.ts`). The session cookie is HttpOnly, so even a script that did run could not read it. |
| Cross-site request forgery (CSRF) | Protected | The session cookie is `SameSite=Lax`, and every cookie-authenticated write, log-in and sign-up included, is refused when its `Origin` or `Sec-Fetch-Site` shows another site (`src/http/middleware/same-origin.ts`). The `/api/v1` routes take a key in the `Authorization` header only, never a cookie, so a cross-site page cannot make a browser send one. |
| Sessions | Protected | A session is 32 random bytes in an `HttpOnly`, `SameSite=Lax` cookie, `Secure` with the `__Host-` prefix in production. The database stores only its SHA-256. Sessions last 30 days, a new one is issued at every log-in, log-out deletes it, and changing the password or turning 2-step codes on or off ends every other session (`src/modules/auth/`). |
| Broken object-level authorisation (BOLA/IDOR) | Protected | Enforced in the data layer. Project and key repositories are built for one signed-in user (`createProjectsRepository(db, userId)`), and every query filters by that owner. Rehearsals are scoped by project id inside the engine, and routes reach a project only through its owner's repository first. Someone else's id reads as 404, never 403. A composite foreign key ties each API key to a project of the same owner. `test/api.test.ts` tries every read and write against a second account, and a rehearsal id under the wrong project. |
| API keys for other apps | Protected | `flk_` plus 32 random bytes. Shown once at creation; only the SHA-256 is stored, with a 10-character prefix for recognising it. A key works for its one project and nothing else, can be revoked at once, and stops working when its project is deleted. Its last use is recorded at most every 10 minutes. Keys are refused anywhere but the `Authorization: Bearer` header. |
| Rate limiting | Protected | Per visitor: 600 API calls a minute. Calls that spend model tokens (starting a rehearsal, asking a follower, asking for launch advice) are capped at 60 per 10 minutes per account, and per API key on `/api/v1` (`src/http/middleware/rate-limit.ts`). Log-in: 10 wrong passwords or codes per 15 minutes per visitor and 50 per email. Sign-up: 5 accounts per visitor per hour. Spend caps in the engine: 10 rehearsals of one draft per day and 25 questions per rehearsal, 5 launch advisor runs per project (`REHEARSALS_PER_SUBJECT_PER_DAY`, `INTERVIEWS_PER_REHEARSAL`, `ADVICE_PER_PROJECT_PER_DAY`; deleting a run does not reset its count). Set `TRUST_PROXY=1` behind Render or Fly. |
| Request size | Protected | Every API body is capped at 64 KB before it is parsed; drafts at 10,000 characters, past posts at 25 of 1,000 characters each. |
| JWT secrets | Not applicable | No JWTs are issued. Sessions and API keys are opaque random tokens checked against the database, so they can be revoked at once. |
| Model keys kept server side | Protected | The model key is read from the environment by the server only. `/api/config` names the provider and model, never the key (`test/api.test.ts` checks this). The web bundle contains no keys. A model base URL must be https, or http on localhost, and may not carry a username or password. |
| Password hashing | Protected | scrypt (N=2^15, r=8, p=3) with a random salt per password, compared in constant time (`src/modules/auth/passwords.ts`). Passwords are 10 to 200 characters. An unknown email still runs a full hash check and gets the same message as a wrong password. |
| Multi-factor authentication | Optional, per account | Account, 2-step codes: standard TOTP (RFC 6238) that works with any authenticator app. Turning it on needs a code; turning it off needs the password and a code. Each code works once. |
| Permissions enforced server side | Protected | Ownership, key scope, spend caps and any gate a source adapter sets (such as the after-the-decision gate in the Creator OS example) are all enforced on the server, not the UI. |
| Prompt injection | Limited | Drafts and questions reach the model as data inside a fixed prompt, and interview prompts tell the follower to stay in character and ignore instructions in the question. The launch advisor wraps every web page it found in `<finding>` tags that the prompt marks as data, keeps a quote only when it appears word for word in the page it cites, and drops citations to pages that were not found; prices are computed from the buyers' answers, not taken from the model. Model output is only ever shown as text, and its JSON is shape-checked before use. Links shown in reports are the search results' own http(s) URLs, opened with `rel="noopener noreferrer nofollow"`. A model can still be talked into odd replies; nothing it says can act on the server. |
| Row-level security (RLS) | Equivalent in the data layer | SQLite has no RLS. Its job is done by the owner-bound repositories (the only code that runs SQL for projects and keys) and the engine's scope on every rehearsal query. If Flockcast moves to Postgres, enable RLS on the same `user_id` and `scope` columns. |
| Webhook signature verification | Not applicable | Flockcast receives no webhooks. |
| Server-side request forgery (SSRF) | Protected | The server only calls the model host, the optional MiroFish URL, and the launch advisor's fixed search hosts (`hn.algolia.com`, `www.reddit.com`, `api.tavily.com`). A user's words become search terms in a query string, never a URL, and responses are capped at 2 MB with a timeout (`engine/advisor/search.ts`). |
| Source maps | Off | `build.sourcemap: false` in `web/vite.config.ts`. Nothing is inlined as a data URL either, so the CSP stays strict. |
| Default credentials | None | There is no built-in account. Sign-up is closed by default: only the first account can be created, and with `REHEARSAL_OWNER_EMAIL` set only that email can create it. Set `REHEARSAL_SIGNUP=open` to let others join. |
| Sensitive data in logs | Protected | Logs carry ids, counts and timings, never drafts, replies or questions. Fields named like `authorization`, `token`, `api_key`, `secret` or `password` are redacted (`src/core/logger.ts`). 500 errors return a request id, not the stack. |
| Account enumeration | Limited | Log-in never says whether an email exists. Sign-up has to say an email is taken; that answer is rate limited. |
| Security headers | On | CSP, HSTS, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, strict referrer policy, and a permissions policy that allows no camera, microphone or location. |
| Vulnerable dependencies | Clean | `npm audit` reports 0 vulnerabilities for the server and the web app (checked 2026-10-09). Run it again before each deploy. |
| Third-party code licences | Kept apart | MiroFish (AGPL-3.0) is optional and runs as a separate, unmodified service that Flockcast calls over HTTP. No MiroFish code is in this repository (`sidecar/mirofish/README.md`). |

Known limits:

- There is no password reset by email, because Flockcast sends no email. Turn on 2-step codes and keep the password in a password manager.
- 2-step secrets are stored as-is in the database, like the password hashes beside them. Keep the database file private and back it up encrypted.
- Rate limits are kept in memory, which suits the single process Flockcast runs as. A second instance would need a shared store.
- Simulated audiences are a rehearsal, not a forecast. The UI and reports say so, and say when a run was an offline estimate.
